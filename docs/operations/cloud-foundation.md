# CareFlow cloud foundation — synthetic operations runbook

Status: F1–F3 code and synthetic verification foundation. This is not go-live approval. The product retains synthetic-only database constraints, DEMO identities and its visible warning. The connected Mac is the development executor; the product deployment contract is one continuously running app and one authoritative SQLite database on durable local disk.

## Supported behavior

- Separate doctor/assistant accounts and existing server-side permissions remain authoritative. Registration/queue → consultation/prescription → assistant preparation/labels → doctor release → handoff → billing/closure remains intact. Stock is deducted at handoff. NO_MEDICATION and the existing full-waiver path remain supported. No partial collection, refund, bank integration or tax receipt is added.
- `CAREFLOW_PROFILE=cloud` requires an explicit canonical HTTPS origin, loopback bind/trusted peer, absolute existing database and secure cookie. The `local` profile preserves local synthetic rehearsal. A cloud database cannot be opened under the local profile to bypass maintenance checks.
- Startup verifies deployment identity, exact migration history, canonical schema, SQLite/FK integrity and clinical/stock/finance evidence. It does not initialize or migrate a cloud file. Missing mount, wrong identity, altered schema, unknown/newer history and pending migrations stop startup.
- Cloud cookies use `__Host-careflow_session`, Secure, HttpOnly, SameSite=Strict and Path=/. Mutation requests require exact Origin and session-bound CSRF. Every idempotent command also carries its captured recovery generation.
- Password admission persists across restarts: five attempts per normalized account/minute across IPs, 30 per IP/minute, two concurrent password operations and at most 1,024 live hashed buckets. Successes also consume admission. The app fails closed if the limiter cannot write. Cloud requests have a 256 KiB body limit, 30-second request timeout and 15-second connection timeout; the proxy must enforce its own ingress limits too.
- Auth/access security evidence contains allowlisted actions, route templates, opaque actor IDs, status and time; request bodies, raw clinical URLs, passwords, cookies and tokens are omitted. Existing business audit is transactionally coupled to the business effect. New append-only evidence and cancellation tables also reject SQLite REPLACE conflicts. This does not protect against an administrator rewriting the underlying file.

## HTTPS and deployment contract

Use [cloud.env.example](../../careflow-pilot/ops/cloud.env.example) as a reviewed configuration reference. It is not a deployment script. Run one app instance on a supported Node/native runtime with an encrypted persistent local filesystem. Keep code, data, staging and secrets separate. Do not use ephemeral/serverless disk, a network filesystem, a second active SQLite copy or overlapping rolling app writers.

Only a reverse proxy on the same host may reach the app's loopback port. Publish HTTPS on the chosen hostname; block app ports at the network boundary. The proxy must replace client forwarding headers: set Host to the configured origin's host, X-Forwarded-Proto to the single value `https`, and X-Forwarded-For to one validated client IP. Strip Forwarded and X-Forwarded-Port; strip X-Forwarded-Host or set it exactly to the configured host. Never append an arbitrary client-supplied forwarding chain. Do not trust a numeric hop count. Terminate TLS with approved automated certificate renewal, HTTPS redirects, supported protocols and external expiry monitoring. Preserve same-origin cookies and avoid logging clinical query strings or request bodies. TLS/provider configuration has not been installed or validated on a target host.

Release artifact contract: build from an identified commit/lockfile; include `dist/client`, both `dist/server` entry points, shared `dist/chunk-*` files and the complete `drizzle` directory. Install production dependencies for the **target OS/architecture**; never copy the Mac's native modules to Linux. Record runtime, native SQLite version and artifact SHA-256s. Run `npm run verify:native-runtime`, unit/integration/browser checks and a synthetic restore on the actual target image. Preserve the previous compatible release and its artifacts. A second-provider/clean-host restore is a portability acceptance gate, not something inferred from passing Mac tests.

## Unknown command outcomes

Network interruption never means a transaction failed. The browser saves only opaque account/key/operation/generation breadcrumbs in sessionStorage; clinical payloads and retry closures remain in memory. Reload or re-login can inspect the original outcome, but never automatically resends a mutation. New intent from that tab/account is blocked while a prior result remains unresolved.

An attempt is bound to its originating account and recovery generation. Session polling that observes a different account, role or generation clears protected query/mutation state and remounts forms. Old attempts cannot execute as the newly logged-in account; a late response cannot populate the new account's screen or erase an unresolved breadcrumb after a context change. Status and cancellation responses are checked against the session context captured when requested. This includes shared-cookie changes caused by another tab.

`GET /api/operations/:key?generation=...` returns only COMMITTED, CANCELLED or UNKNOWN for the current actor and permitted operation. Missing evidence is UNKNOWN. Cancellation records a permanent tombstone in the same SQLite transaction boundary used by commands, fencing delayed requests. A committed result wins over cancellation; replay of the same immutable request uses existing idempotency evidence. Domain uniqueness/revision guards still protect different-key attempts and competing actors. Clearing browser storage is not an approved recovery procedure. The first release has no offline queue or two-way sync: use paper/old-system downtime records and reconcile physical handoffs/payments before continuing.

## Backup adapter and key custody

`createEncryptedBackup` uses `better-sqlite3`'s online backup API on the owning connection; it never copies only the live main file or forces a checkpoint during an active request. Identity, migration hashes, event/command high-water marks and counts are read from the completed snapshot. SQLite/FK/schema/business validation precedes encryption. Manifest start/end describe the snapshot operation, not a promise that every wall-clock event before the end is included.

`BackupStore` is the provider boundary: immutable create, retrieval for full ciphertext SHA-256/size read-back, and durable immutable `publishReceipt` with its own verification outside the app. Only then is last-verified status advanced and a local append-only verification event recorded. A receipt failure leaves an unadvertised archive; a later metadata failure leaves a recoverable externally indexed archive but reports failure. Adapters must bound and cancel network I/O, use no overwrite/delete/retention-changing credential and meet approved region/versioning/retention requirements. The backup coordinator is injectable into the app, coalesces overlap, starts an immediate run, waits for in-progress work on shutdown and emits only an allowlisted failure event. An actual remote adapter, schedule and alert destination are **not wired into the executable** before provider approval.

The included `DirectoryBackupStore` is a private local **synthetic fixture only**. Its `.cfbak.receipt.json` recovery index is saved beside the archive. It is always identified as `synthetic-directory` and cannot make cloud readiness pass. Do not relabel a local directory as external. A real provider adapter must prove independence from app host/volume failure, retention lock, denied deletion, read-back and a separate decrypt/restore drill.

The `.cfbak` archive is a standard binary RFC 9580 OpenPGP message produced by pinned [OpenPGP.js 6.3.2](https://github.com/openpgpjs/openpgpjs). The runner requires one version 6 public recovery key advertising SEIPDv2 AES-256/GCM support, rejects negotiated legacy modes, and encrypts without compression and delegates key wrapping, authenticated encryption framing and verification to the library. CareFlow's encrypted payload is a four-byte manifest length, JSON manifest and the SQLite file; it has no custom cryptographic envelope. Decryption rejects any parsed message without the required SEIPDv2 AES-256/GCM packet before consuming plaintext. The 64-hex key fingerprint must match the trusted receipt. The complete encrypted stream must authenticate before a database is exposed for validation. The current reviewed pack limit is 8 GiB; larger datasets require a separate capacity review. An interoperability test decrypts an archive directly with OpenPGP.js without CareFlow's decoder.

The app receives only an armored public key. A separate recovery runner/operator holds the private key in an approved secret custody system, with an independently tested recovery method and rotation procedure. The current runner accepts an already unlocked armored v6 private key supplied through a private file on that isolated runner; approved secret retrieval/unlocking is a provider integration gate. Never put it in app storage, Git, build artifacts or the archive. Only ephemeral test keys have been generated during development. A 0700 staging directory must be on encrypted disk; files are 0600 and ordinary error/success cleanup removes plaintext. A process kill can leave `.restore-*`, `snapshot-*` or `migration-*` staging files: after proving no live owner, inspect and remove only abandoned staging on the isolated runner. Partial files without verified receipts are not valid backups. Deletion does not guarantee secure erasure on SSDs.

## Explicit maintenance CLI

Run from `careflow-pilot`. The source runner is `npm run operations --`; the built runner is `node dist/server/operations.js`. Every command requires `--db /absolute/path --environment <environment-id> --confirm SYNTHETIC-ONLY`. Stop the app before CLI operations that acquire its host lock. Scheduled online backup instead uses the existing app connection. No command starts or provisions a cloud service.

| Command | Additional inputs and result |
| --- | --- |
| `initialize` | A completely new target; creates synthetic schema and a private `<db>.deployment.json` containing environment, database UUID and recovery generation. Never adopts an existing clinical database. |
| `status` | Optional `--max-backup-age <seconds>`; reports safe health reasons. Exit zero means the query ran, not that `ready` is true. |
| `backup` | `--public-key-file --staging --synthetic-store --release-id --receipt-file`, all paths absolute. Writes new archive/receipt objects and an additional operator receipt file with exclusive create. |
| `migrate` | Same backup inputs. Holds the exclusive host lock, verifies an encrypted pre-migration backup, applies migrations to a disposable copy and validates it before the source transaction. Clears sessions after applying. |
| `restore` | `--archive --receipt-file --private-key-file --target --expected-database-id --fencing-evidence`. Unused isolated target only. Optional `--allow-pending-migrations` accepts only a known cloud schema prefix (0025 or later); this stays quarantined and requires a separate `migrate` before startup. |
| `restore-drill` | Restore inputs plus `--operator-ref`. `--db` identifies the stopped source. Verifies matching source identity/generation, then records a separate successful decrypt/restore drill on it. |
| `approve-recovery` | `--approval-file` with the strict fields below. Requires fresh credentials and separately retained doctor/operator reconciliation records. |

Commands do not print secrets or raw failure details. On a failure preserve the original database, sidecars, locks, successful external receipt and release bundle for investigation; do not repeatedly initialize or reset. Schema history 0000–0023 is unchanged. New snapshots describe 0024 security evidence, 0025 recovery/cancellations and 0026 backup verification evidence. Published SQL must never be edited to make a failed migration appear valid. Keep source migration/application stopped on failure; no automatic downgrade or data replay is performed.

Host locks are never removed just because they are old. Verify process/service termination and storage identity, fence old ingress/writers, retain incident evidence, and use the reviewed operator recovery process. A copied stale database and its copied deployment record cannot prove the old host is fenced; infrastructure fencing is a separate operator responsibility.

## Restore and reconciliation

1. Stop writes and fence the old app/host before activating any replacement. Retain downtime records, incident/fencing reference, the trusted externally stored receipt and release/schema identity. Restore into a new isolated private directory, never over the source.
2. Match environment/database/key/manifest/checksums, decrypt, validate migrations, schema, SQLite/FKs and the clinical/stock/finance evidence chain. The runner deletes restored sessions and rate buckets, rotates recovery generation and records a restore event. **All restored accounts are inactive** with forced password change; mode remains `reconciling`.
3. Compare the completed snapshot's cutoff, event/command high-water marks and post-cutoff external/paper evidence. Check clinical records, physical medication handoffs, reservations/stock counts, collected cash/manual PromptPay confirmations, closures, current staff roster and previously disabled accounts. Unknown old browser intents stay fenced. Never repeat a physical action merely because restored command evidence is absent.
4. Reset credentials through the existing offline `users` CLI, using the cloud profile/environment, for only the independently reviewed current accounts. The recovered old hash is insufficient. Keep unapproved accounts disabled. Retain separate doctor/operator approvals outside the app; CLI reference strings are attestations, not digital signatures or proof that a reconciliation happened.
5. Submit a strict approval JSON containing `restoreId`, current `generation`, distinct `operatorRef` and `doctorApprovalRef`, `doctorId`, `clinicalRef`, `stockRef`, `financeRef`, `cutoffRef`, `accountRef`, `approvedAccountIds`, and `cutoffDisposition: "NO_UNRECORDED_EFFECTS"`. The approving doctor must be in the approved roster with fresh credentials. Approval clears sessions again and enables only the reviewed accounts with another mandatory password change.
6. If any physical event is missing after the backup cutoff, **do not attest NO_UNRECORDED_EFFECTS**. Recovery remains closed pending the separately reviewed clinical/stock/finance correction workflow in F4. This foundation deliberately does not synthesize missing notes, payments or stock movements. Old-generation cancellations are allowed only after explicit no-missing-effects reconciliation; old payload replay remains fenced.
7. Reconfigure and verify a new external backup plus a matching-key restore drill for the recovered generation. Check health and inspect clinical/financial reconciliation before any approved reopening. A saved old drill/backup status is cleared during restore.

## Monitoring and remaining gates

`/api/live` is process liveness. `/api/ready` is a minimal public ready/not-ready signal through the trusted HTTPS proxy. Doctor-authorized `/api/operations/health` gives allowlisted reasons for recovery mode, disk free space, WAL size, backup age/identity/storage domain and restore-drill evidence. Filesystem paths, raw SQL and patient details are omitted. Baseline disk/WAL guards are 512 MiB free / 256 MiB WAL; review these thresholds on the target workload. SQLite quick-check is cached for at most 60 seconds and a detected failure remains latched until restart/investigation.

Backup age is conservatively measured from snapshot start, not upload verification time; slow upload cannot make old data appear fresh. Receipt timestamps and recovery generation must also match.

Critical disk/WAL/database/recovery failures block cloud business writes. Setting `CAREFLOW_BACKUP_MAX_AGE_SECONDS` activates backup/readiness-related write holds; its value must be approved and measured. With no backup-age policy, synthetic development can still mutate but cloud readiness stays false. Login/logout remain available where storage works; unknown commands remain unresolved until checks recover. No 15-minute RPO or 60-minute RTO guarantee has been agreed or demonstrated.

The provider phase must wire independent external uptime/TLS checks, disk/WAL/corruption/backup-age alerts, low-noise security monitoring, retention and restore-drill cadence, and prove delivery to the named operator. In-process checks alone cannot report a dead host. Run restore drills after key/schema/backup-path changes and on an agreed schedule, and measure actual cutoff and recovery time with nonempty synthetic data.

Local failure tests cover SIGKILL before and after a command commit, SQLite page-limit exhaustion returning SQLITE_FULL, staging permission failure, ciphertext/read-back corruption, receipt publication failure and local metadata failure after external indexing. These are process/storage fault tests on the Mac. Target-host reboot, actual filesystem exhaustion, interrupted backup/migration at each phase, operating-system durability and infrastructure fencing remain deployment acceptance work.

Independent work delivered: runtime boundary, durable auth admission/audit, command-outcome recovery, isolated encrypted backup/restore/migration tooling, operational contracts and schema-independent import staging. Remaining decisions/acceptance: provider and data region, cost/retention and backup age policy, public DNS/TLS/secret custody, real remote adapter and alert delivery, target Linux/runtime and clean-host portability, MFA/real-patient schema/security review, missing-event correction workflow, actual printer/scanner tests, and go-live authorization. No purchase, persistent credential, deployment or live patient upload was performed.

Legacy migration is a future reviewed adapter. `src/server/import/staging.ts` accepts only explicitly synthetic source envelopes, preserves source IDs and hashes, quarantines ambiguous/conflicting rows, defaults unknown allergies to UNKNOWN, and returns allowlisted dry-run results with zero applied records. It assumes no old-system table or export format, performs no live read and creates no clinical, payment or stock event. Wait for the user's access/export and mapping review before adding a parser or production import.
