# CareFlow — แบบแผนหลักสำหรับ Production Trial ที่คลินิกบน Windows

วันที่: 20 กันยายน 2026

สถานะ: **รอทบทวนเอกสารฉบับเขียน — ยังไม่ใช่การอนุมัติเปิดใช้กับคนไข้จริง**

เอกสารนี้เป็นแบบแผนหลักและเกณฑ์ตรวจรับสำหรับส่งต่องาน ไม่ใช่ implementation plan รายไฟล์ที่อนุมัติแล้ว ไม่ใช่ตัวติดตั้ง และไม่ได้ทำให้รุ่นปัจจุบันรองรับข้อมูลจริงโดยอัตโนมัติ งานแต่ละส่วนต้องมีแบบย่อยและแผนทดสอบก่อนลงมือพัฒนา

เริ่มรับงานบน Windows ที่ [คู่มือส่งต่องาน](../../handoff/clinic-windows-start-here-th.md)

## 1. สิ่งที่ตกลงและความหมายของคำว่า “พร้อม”

ผู้ใช้ยืนยันว่า:

- ใช้ [ajbk/careflow-clinic](https://github.com/ajbk/careflow-clinic) เป็น repository หลัก
- เป้าหมายคือ trial run กับคนไข้จริงที่คลินิก ไม่ใช่เพียงซ้อมข้อมูลจำลอง
- ใช้หลายเครื่อง แยกผู้ช่วยและแพทย์ บน Windows ในเครือข่ายคลินิก
- ใช้ CareFlow ควบคู่กับระบบเดิมก่อน ไม่เปลี่ยนทั้งหมดในวันแรก
- จะนำฐานข้อมูลเดิมมาให้วิเคราะห์โครงสร้างภายหลัง ยังไม่ได้ส่งไฟล์หรือระบุชนิดฐานข้อมูล

ข้อเสนอที่ให้ทบทวนในแบบนี้:

- ระบบเดิมเป็นหลักอ้างอิงด้านตัวตน เวชระเบียน ใบเสร็จ และยอดปิดวันระหว่าง trial; CareFlow บันทึกคู่ขนานเพื่อพิสูจน์ workflow
- Windows เครื่องหลักหนึ่งเครื่องให้บริการเว็บแก่เครื่องผู้ช่วย/แพทย์ผ่าน HTTPS เฉพาะ LAN คลินิก ยังไม่เปิดรับจากอินเทอร์เน็ต
- เริ่มฐาน CareFlow สำหรับคลินิกใหม่ แยกจากฐาน UAT ทั้งหมด ไม่เปลี่ยนฐานจำลองให้เป็นฐานจริง
- เตรียมการติดตั้ง ความปลอดภัย และการกู้คืนได้โดยไม่รอฐานเดิม แต่ห้ามเดาวิธีนำเข้าข้อมูลเก่า
- การนำเข้าประวัติย้อนหลังทั้งฐานไม่ใช่เงื่อนไขเริ่ม trial หากยังค้นประวัติจากระบบเดิมได้ และตรวจเทียบตัวตน/รายการปัจจุบันได้ครบทุกคน

“พร้อมสำหรับ trial” ต้องหมายถึงผ่านทั้งการตรวจซอฟต์แวร์และการตรวจที่คลินิก มีผู้รับผิดชอบอนุมัติเป็นลายลักษณ์อักษร การผ่าน CI หรือเปิดหน้า login ได้อย่างเดียวไม่เพียงพอ และการจบ trial ยังไม่ใช่การอนุมัติเลิกระบบเดิม

## 3. ทางเลือกและสถาปัตยกรรมที่เสนอ

**ทางเลือก A — เครื่องหลัก Windows ภายในคลินิก: แนะนำสำหรับรอบนี้** ต่อยอดโค้ดและโครงสร้างฐานข้อมูลเดิม แต่สร้างฐานใช้งานจริงใหม่ เก็บข้อมูลในคลินิก และตั้งเป้าให้ workflow ทำงานได้เมื่ออินเทอร์เน็ตขาดแต่ LAN/เครื่องหลักยังปกติ แลกกับการที่คลินิกต้องดูแลเครื่องหลัก ไฟฟ้า สำรองข้อมูล และผู้รับผิดชอบกู้คืน

**ทางเลือก B — ระบบส่วนกลางบน Cloud:** ลดการพึ่งเครื่องหลักหน้างาน แต่ต้องออกแบบการดูแลข้อมูลนอกคลินิก ค่าใช้จ่าย การเข้าถึง และแผนเมื่ออินเทอร์เน็ตขาดเพิ่ม ยังไม่อยู่ในขอบเขตที่เสนอ

องค์ประกอบของทางเลือก A:

1. เครื่องผู้ช่วย/แพทย์ใช้ browser และบัญชีส่วนบุคคล ไม่ติดตั้งฐานข้อมูลแยกเครื่องและไม่ sync ฐานระหว่างเครื่อง
2. HTTPS reverse proxy บนเครื่องหลักรับเฉพาะเครือข่ายที่อนุมัติ แล้วส่งต่อไปแอปที่ยังฟัง `127.0.0.1`; ไม่เปิดพอร์ตแอป `3001` ให้ LAN โดยตรง
3. แอปหนึ่งชุดเป็นผู้เขียนฐาน SQLite บน local NTFS เครื่องหลัก ไม่ใช้ shared drive, OneDrive หรือ network filesystem สำหรับฐานที่กำลังใช้งาน ข้อจำกัดนี้สอดคล้องกับ [SQLite WAL](https://www.sqlite.org/wal.html)
4. เสนอ Caddy เป็น HTTPS proxy และใช้ certificate ภายในที่ติดตั้งความเชื่อถืออย่างถูกต้องทุกเครื่อง ไม่สอนให้ผู้ใช้กดข้ามคำเตือน certificate; การ trust บนเครื่องหลักไม่ได้ทำให้เครื่องอื่น trust ตาม ([Caddy local HTTPS](https://caddyserver.com/docs/automatic-https))
5. แอปและ proxy ทำงานเป็น Windows services ภายใต้สิทธิ์จำกัด เปิดหลัง restart โดยไม่ต้องเปิด Terminal ค้าง; รายละเอียด wrapper และรุ่น binary ต้องตรึงในแผนติดตั้ง ([Caddy Windows service](https://caddyserver.com/docs/running#windows-service))
6. สำรองผ่านกลไก SQLite ที่ให้ snapshot สอดคล้องกัน เช่น [Online Backup API](https://www.sqlite.org/backup.html) ไม่คัดลอกเฉพาะ `.sqlite` ขณะระบบกำลังเขียน แล้วสร้างสำเนาเข้ารหัสนอกเครื่องหลัก

เครื่องหลักเป็นจุดที่ถ้าเสียแล้ว CareFlow หยุดทั้งคลินิก รุ่น trial นี้ไม่อ้างว่าเป็นระบบ high availability; ระบบเดิมและขั้นตอน downtime เป็นทางดำเนินงานต่อ

## 4. กติกาใช้งานคู่ขนาน

### 4.1 หนึ่งเหตุการณ์จริง บันทึกสองระบบ

- ยืนยันตัวตนจากแหล่งเดิมและคนไข้ก่อนเปิด Visit; ต้องมีรหัสอ้างอิงที่เชื่อมคนเดียวกันข้ามระบบ ไม่จับคู่ด้วยชื่ออย่างเดียว
- การตรวจ จ่ายยา และรับเงินจริงเกิดเพียงครั้งเดียว ห้ามเรียกเก็บหรือส่งมอบซ้ำเพื่อให้สถานะ CareFlow เดินครบ
- ระบุให้ชัดว่าฉลาก/เอกสารใดส่งมอบจริง ฉลากทดสอบต้องแยกจากฉลากจ่ายยาและทำลายอย่างเหมาะสม ไม่วางปะปน
- ผู้รับผิดชอบบันทึกทั้งสองระบบและตรวจผลก่อนจบรายการ หากต้องบันทึกตามหลัง ต้องเก็บเวลาที่เกิดเหตุการณ์จริงแยกจากเวลาบันทึก พร้อมเหตุผล ห้ามสร้างลายเซ็นหรือเวลาย้อนหลังปลอม
- CareFlow ยังไม่ออกใบเสร็จทางการในขอบเขต trial นี้ ใช้ใบเสร็จเดิมครั้งเดียวและเก็บเลขอ้างอิงเพื่อเทียบเงิน
- PromptPay ในรุ่นเดิมเป็นการยืนยันโดยคน ไม่ใช่หลักฐานจากธนาคารหรือระบบรับเงินอัตโนมัติ

### 4.2 เมื่อข้อมูลไม่ตรงกัน

ไม่แก้สองระบบอัตโนมัติ ไม่เขียนทับหลักฐานที่ลงนามแล้ว ให้หยุดขั้นตอนที่เกี่ยวข้องและให้แพทย์/ผู้รับผิดชอบการเงินตรวจจากหลักฐานต้นทาง ระบบเดิมเป็นหลักอ้างอิงในการดำเนินงานระหว่าง trial แต่ไม่ใช่เหตุให้ละเลยข้อผิดพลาดที่พบในระบบเดิมเอง

ข้อมูลที่ลงนามหรือยืนยันแล้วต้องแก้ด้วยประวัติการแก้ไข เหตุผล และผู้รับผิดชอบที่ตรวจย้อนหลังได้ งานนำเข้าหรือผู้ดูแลระบบไม่มีสิทธิ์สร้างลายเซ็นแพทย์แทนเจ้าของข้อมูล

### 4.3 ตรวจปิดวัน

ตรวจเทียบจำนวนคน/Visit และรายการที่ค้าง ยาและจำนวนที่จ่ายจริงต่อรายการ ยอดเงินสด/โอน/ยกเว้น/เลขใบเสร็จ และยอดคลัง พร้อมเหตุผลของความต่าง แยกวันที่เกิดเหตุการณ์ตามเวลาไทยออกจากวันนำเข้าหรือวันบันทึกตามหลัง

ทะเบียนเทียบที่มี HN หรือรายละเอียดคนไข้ต้องอยู่ในพื้นที่คลินิกที่จำกัดสิทธิ์ ไม่บันทึกลงเอกสาร Git หรือแนบใน issue สาธารณะ

## 5. งานที่ต้องทำก่อนคนไข้จริงรายแรก

### A. แยกข้อมูลจริงออกจากข้อมูลจำลอง

- กำหนดชนิดฐานข้อมูลอย่างชัดเจนตั้งแต่สร้าง และตรวจที่ server/maintenance ทุกทางเข้า; production ต้องไม่เปิดฐานผิดชนิดหรือสร้างฐานว่างเองเพราะ path ผิด
- ฐาน UAT เดิมและประวัติ snapshot ต้องยังอ่านได้ ไม่ล้าง/แก้เนื้อหาเพื่อให้ผ่านรูปแบบใหม่
- เพิ่ม migration แบบไปข้างหน้า พร้อมทดสอบอัปเกรดฐานที่มีข้อมูลและ rollback ของ migration ที่ล้มเหลว ไม่แก้ไฟล์ `0000`–`0023`
- การเริ่มฐานจริงต้องเป็นขั้นตอน bootstrap ที่ระบุปลายทางและผ่านการตรวจรับ ไม่ใช่สวิตช์บนฐาน UAT; DEMO seed ต้องไม่กลายเป็นรายการยาจริงที่ใช้งานได้
- คำสั่ง reset/expire-session สำหรับ UAT ต้องปฏิเสธฐานจริงก่อนเขียนข้อมูล และไม่อยู่ในเส้นทางใช้งานประจำของชุดคลินิก

### B. ตัวตนคนไข้และความถูกต้องทางคลินิก

- รองรับลงทะเบียนคนไข้จริง ค้นคนไข้เดิม กลับมารับบริการ และแก้ข้อมูลประชากรอย่างมี audit; ใช้ ID ภายในที่ไม่ขึ้นกับชื่อหรือเลข HN เก่า
- เก็บ HN/รหัสต้นทางเป็นข้อความ รักษาศูนย์นำหน้า และแยกแหล่งที่มา ป้องกันการสร้างคนเดียวกันซ้ำทั้งจากคนบันทึกพร้อมกันและจากการนำเข้า
- ตรวจวันเกิด/อายุ รูปแบบ พ.ศ.–ค.ศ. และข้อมูลที่ไม่ทราบอย่างชัดเจน ไม่ใส่วันเกิดหรือเบอร์โทรสมมติเพื่อผ่าน validation
- ประวัติแพ้ยาต้องรองรับ “แพ้”, “ไม่มีประวัติแพ้ที่ทราบ” และ “ยังไม่ทราบ/ยืนยันไม่ได้”; ค่าว่างจากฐานเก่าห้ามถูกแปลเป็น “ไม่แพ้” อัตโนมัติ
- ผู้ช่วยเก็บคำตอบเบื้องต้น แพทย์ทบทวนก่อนตัดสินใจรักษา; ต้องเห็นข้อมูลแพ้ยาที่เกี่ยวข้องระหว่างตรวจและจ่ายยา ไม่อ้างว่าระบบตรวจปฏิกิริยาระหว่างยาหรือคำนวณขนาดยาได้ถ้ายังไม่มีความสามารถนั้น
- ระบุรายการที่ข้อมูลไม่พออย่างเด่นชัดและไม่ให้ลงนาม/จ่ายยาต่อด้วยข้อมูลที่ไม่ผ่านเงื่อนไขความปลอดภัยที่แพทย์อนุมัติ
- คงหลักฐานลงนามแบบแก้ทับไม่ได้ การแก้คำสั่ง การยกเลิกการจัดยา และการป้องกันจ่ายซ้ำ พร้อมทดสอบกลับมาเปิดข้อมูลคนไข้เดิม

### C. ยา คลัง และเงินที่ตรวจเทียบได้

- ให้ผู้มีสิทธิ์จัดการรายการยาจริง ความแรง รูปแบบ หน่วย บาร์โค้ด ราคา และสถานะใช้งาน; ให้แพทย์ตรวจรายการที่จะใช้ใน trial
- หน่วยสั่ง หน่วยหยิบ และหน่วยขายต้องตรงกัน หรือมีวิธีแปลงที่ผ่านการอนุมัติ ห้ามจับคู่ยาด้วยชื่อ/บาร์โค้ดที่คลุมเครือแล้วใช้ทันที
- เริ่มคลังจากยอดนับจริง ณ จุดตัดที่บันทึกไว้ พร้อมล็อต วันหมดอายุ และราคาที่ตรวจสอบได้; ห้ามนำเข้ายอดปัจจุบันแล้ว replay การจ่ายย้อนหลังซ้ำ
- รองรับราคาคลินิกจริงและเก็บ snapshot ณ เหตุการณ์; แก้ราคาปัจจุบันแล้วต้องไม่เปลี่ยนประวัติที่ลงนาม/ชำระแล้ว
- เงินแสดงเป็นบาท แต่รุ่นปัจจุบันเก็บจำนวนเต็มบาทเท่านั้น ถ้าราคาหรือยอดจากระบบเดิมมีสตางค์ ต้องออกแบบหน่วยเงินและ migration ก่อนรับข้อมูลนั้น ห้ามตัดเศษหรือปัดเองโดยไม่แจ้ง
- เพิ่มการอ้างอิงใบเสร็จเดิมและรายงานเทียบปิดวัน สิทธิ์คิดเงิน/ยืนยันโอน/ยกเว้น/ปิด Visit ต้องยังตรวจที่ server ตามบทบาทเดิม
- กรณีรับบางส่วน คืนเงิน หรือรายการนอกขอบเขต ให้ทำในระบบเดิมและบันทึกข้อยกเว้น ไม่บิดยอดหรือสถานะ CareFlow เพื่อจำลองว่าได้รับการรองรับแล้ว

### D. สิทธิ์ ความปลอดภัย และข้อมูลส่วนบุคคล

- ใช้บัญชีบุคลากรแต่ละคน ไม่ใช้บัญชี/รหัสทดลองร่วมกัน; ผู้ช่วยต้องไม่เห็น SOAP/OPD หรือทำสิ่งที่เป็นสิทธิ์แพทย์โดยเปลี่ยน URL หรือยิง API
- แยกผู้ดูแล Windows/การติดตั้งออกจากสิทธิ์แพทย์ ไม่ให้สิทธิ์ทางคลินิกเพียงเพราะเป็นผู้ติดตั้ง
- production ใช้ HTTPS, Secure/HttpOnly cookies และตรวจ origin/host ของคำขอเปลี่ยนข้อมูล รวม login; trust proxy เฉพาะขอบเขตที่ตั้งไว้ และไม่เปิด CORS กว้าง
- ทดสอบ logout ของคนหนึ่งไม่กระทบบัญชีอีกคน, session หมดอายุ, เปลี่ยนรหัส/ปิดบัญชีระหว่างมีคำขอค้าง และหน้าจอไม่ค้างข้อมูลคนก่อนหลังเปลี่ยนบัญชี
- จำกัด ACL ของโปรแกรม/config/data/backup/log ตามหน้าที่; บัญชี service ไม่เป็น administrator และบุคลากรทั่วไปไม่เปิดไฟล์ฐานข้อมูลได้โดยตรง
- เข้ารหัสดิสก์และสำเนาสำรอง เก็บ recovery key แยกจากเครื่อง/สำเนานั้น ทดสอบการปลดล็อกโดยผู้รับผิดชอบ; การเข้ารหัสไม่แทนการจำกัดสิทธิ์ ([Microsoft: recovery-key backup](https://support.microsoft.com/en-us/windows/security/encryption/back-up-your-bitlocker-recovery-key))
- จำกัดข้อมูลใน logs, URL, diagnostics, screenshots และ print spool; ไม่ส่ง PHI, password, token, private key หรือฐานข้อมูลขึ้น GitHub/แชต/ระบบ telemetry โดยอัตโนมัติ
- ก่อนเปิดจริง เจ้าของคลินิกต้องยืนยันผู้รับผิดชอบข้อมูล วัตถุประสงค์และฐานการประมวลผล การแจ้งผู้ป่วย สิทธิ์เข้าถึง ระยะเวลาเก็บ และขั้นตอนรับมือเหตุข้อมูลรั่วกับผู้รับผิดชอบที่เหมาะสม เอกสารนี้ไม่ใช่การรับรองทางกฎหมายหรือการรับรอง PDPA

### E. Windows ที่ดูแลและกู้คืนได้

- แยกโปรแกรมแต่ละรุ่นออกจากข้อมูล เช่นโปรแกรมใน `C:\Program Files\CareFlow\releases\` และข้อมูลใน `C:\ProgramData\CareFlow\clinic-data\clinic.sqlite`; เส้นทางจริงต้องบันทึกและตรวจ ACL ไม่อยู่ใน checkout, OneDrive, WSL หรือ shared folder
- มี preflight ตรวจ Windows/architecture/runtime ที่รองรับ, native binaries, ที่ว่าง, ACL, DNS/IP, certificate, เวลาเครื่อง, พอร์ต และเส้นทางฐาน ก่อนติดตั้งหรือเปิดรับข้อมูล
- กำหนดเครื่องหลักที่เปิดระหว่างคลินิกทำงาน แผน Windows Update/การ sleep/ไฟดับ และเครื่องสำรองไฟตามสภาพหน้างาน ไม่สัญญาว่าเครื่องใดผ่านก่อนทดสอบจริง
- service ต้องหยุดอย่างปลอดภัย ตรวจฐาน/maintenance state ก่อนเริ่ม และไม่เปิดสอง host เขียนฐานเดียวกัน; การกู้ stale lock ต้องพิสูจน์ว่าไม่มีเจ้าของล็อกเดิม ไม่ลบล็อกตามอายุเพียงอย่างเดียว
- ถ้าหยุดเพราะความถูกต้องของข้อมูลหรือเหตุความปลอดภัย ต้องมีสถานะปิดงานเขียนที่คงอยู่หลัง restart; auto-start ต้องไม่ยกเลิกคำสั่งหยุดนั้น
- การ upgrade ต้องมีจุดหยุดรับรายการ สำรองที่ยืนยันแล้ว ตรวจ schema compatibility และบันทึก release; production ไม่ migrate เงียบ ๆ เพียงเพราะเริ่ม process รุ่นใหม่
- มีหน้าสถานะ/เครื่องมือตรวจ readiness สำหรับผู้มีสิทธิ์ แสดงรุ่น สถานะฐาน ที่ว่าง และอายุสำเนาสำรอง; `/api/health` แบบ `SELECT 1` ไม่ใช่ใบผ่าน go-live และ endpoint สาธารณะต้องไม่เผย path หรือข้อมูลคลินิก

### F. Backup, restore และเป้าหมายการฟื้นตัว

เสนอเป้าหมายให้เจ้าของคลินิกยอมรับก่อนเปิด: สำเนานอกเครื่องหลักที่กู้ได้ต้องใหม่ไม่เกิน **15 นาทีขณะเปิดบริการ** และกู้ CareFlow บนเครื่องทดแทนภายใน **60 นาที** ในการซ้อมจริง เป้าหมายนี้ไม่ใช่ความสามารถที่มีแล้ว และไม่ใช่การยอมรับให้สูญข้อมูลช่วงดังกล่าวโดยไม่ตามตรวจ

- สำรองแบบ snapshot ที่สอดคล้องกัน แล้วตรวจ identity/migration, integrity และความสัมพันธ์ข้อมูลก่อนประกาศสำเร็จ
- เก็บ manifest ที่มีรุ่นแอป รุ่นฐาน เวลา snapshot และ checksum; ไม่ใส่ข้อมูลคนไข้/รหัสลับใน manifest ที่ส่งให้ผู้พัฒนา
- ส่งสำเนาเข้ารหัสที่เสร็จสมบูรณ์ไปอีกอุปกรณ์ตามรอบ และมีสำเนารายวันแบบถอดการเชื่อมต่อ/แยกสถานที่เก็บที่เจ้าของคลินิกควบคุม; สำเนาบนดิสก์เดียวไม่ผ่านเกณฑ์เครื่องเสีย
- การส่งไฟล์ backup สำเร็จไปที่เก็บภายนอกไม่ใช่การแชร์ฐาน SQLite ที่กำลังเปิดใช้งาน
- ใช้การเก็บแบบหลายรุ่น ไม่เขียนทับสำเนาดีล่าสุดเมื่อการสำรองใหม่ล้มเหลว; กำหนดระยะเก็บ/ความจุและวิธีหมุนเวียนในแผนย่อยที่เจ้าของข้อมูลอนุมัติ ก่อนเริ่มจริงห้ามเปิดการลบตามอายุโดยยังไม่มีนโยบาย
- แจ้งเตือนเมื่อสำรองล้มเหลว/เก่าเกินเกณฑ์ ดิสก์เต็ม หรือกู้ไม่ได้; งดเริ่ม Visit ใหม่ใน CareFlow และใช้ระบบเดิม โดยไม่หยุดการดูแลคนไข้
- ซ้อมกู้ในพื้นที่แยก ไม่ทับฐานต้นทาง พร้อมตรวจคนไข้ ประวัติแพ้ยา หลักฐานลงนาม ล็อต ยอดเงิน และเอกสารก่อน/หลัง restore; บันทึก snapshot cutoff และเวลาที่ใช้จริง
- ฐานที่กู้ต้องไม่ทำให้ session เก่ากลับมาใช้ได้; มีขั้นตอนยกเลิก session หลัง restore และตรวจบัญชีที่เคยถูกปิด/เปลี่ยนสิทธิ์หลัง snapshot ก่อนเปิดระบบ
- ถ้ามีธุรกรรมหลัง snapshot ต้องเทียบและบันทึกกลับจากหลักฐานระบบเดิมโดยผู้มีสิทธิ์ ห้ามส่งมอบยา รับเงิน หรือตัดสต็อกจริงซ้ำเพื่อเติมข้อมูล

## 6. งานฐานข้อมูลเดิม — แยกจากการเปิดใช้งาน

### 6.1 ขอบเขตที่อนุญาตตอนนี้

ขณะเขียนเอกสารยังไม่ได้รับฐานเดิม ไม่มีการเชื่อมต่อ คัดลอก อ่านข้อมูลคนไข้ หรือวิเคราะห์ชนิดฐานจริง การที่ผู้ใช้จะส่งมาให้ภายหลังไม่ใช่สิทธิ์ให้นำเข้าหรือแก้ฐานที่คลินิกโดยอัตโนมัติ

### 6.2 ลำดับเมื่อได้รับอนุญาตและมีไฟล์

1. **ตรวจสิทธิ์และรับอย่างปลอดภัย:** ยืนยันระบบเจ้าของไฟล์ ชนิด/รุ่นฐาน วิธีสร้าง backup ที่สอดคล้องกัน เวลา cutoff และสิทธิ์ของผู้ส่ง ไม่ขอรหัสระบบจริงในแชต ไม่อ่านฐาน live เพื่อสะดวกกว่าการใช้สำเนา
2. **เริ่มจากโครงสร้าง:** ดู schema, ตาราง, primary/foreign keys, indexes และคำอธิบายที่ผ่านการตรวจว่าไม่มีข้อมูลลับก่อน ใช้ตัวอย่างข้อมูลจำลองหรือที่ปกปิดตัวตนอย่างเหมาะสมเมื่อจำเป็น
3. **แยกพื้นที่วิเคราะห์:** เก็บต้นฉบับพร้อม checksum แบบไม่แก้ไข แล้ววิเคราะห์สำเนาในเครื่อง/พื้นที่ที่คลินิกอนุมัติ ข้อมูลจริงไม่เข้าชุดทดสอบ Git หรือ output ของผู้ช่วย AI; เครื่องมือวิเคราะห์ต้องรายงานเฉพาะ metadata/ผลตรวจที่ลดข้อมูลแล้ว
4. **ตรวจรูปแบบก่อน restore:** ไม่รันไฟล์ dump, stored procedure, trigger หรือ extension ที่ได้รับโดยอัตโนมัติ; ถ้าต้อง restore เพื่อสำรวจ ให้ทำในระบบแยกที่ไม่มีสิทธิ์ไปฐาน live หรือเครือข่ายอื่น
5. **จัดทำ data dictionary และ mapping:** เชื่อมตัวตน/ข้อมูลประชากร Visit/เวชระเบียน แพ้ยา ยา/หน่วย ล็อต/การเคลื่อนไหว ราคา/การรับเงิน และเอกสารอ้างอิง พร้อมที่มาหรือความไม่แน่ใจของแต่ละข้อ
6. **ให้เจ้าของข้อมูลยืนยันความหมาย:** ชื่อคอลัมน์เพียงอย่างเดียวไม่พิสูจน์ว่าเป็นยอดรับเงินจริง วันรับบริการ หน่วยบาท หรือสถานะแพ้ยา ต้องตรวจจากพฤติกรรมระบบเดิมและคำยืนยันของผู้รับผิดชอบ
7. **ทำ dry run ก่อน:** ทดลองนำเข้าในฐาน staging แยก ตรวจจำนวนแถว ความสัมพันธ์ ผลรวม ข้อซ้ำ และตัวอย่างที่ผู้มีสิทธิ์ตรวจในคลินิก เก็บรายการที่ตีความไม่ได้เป็นข้อยกเว้น ไม่เดาแล้วนำเข้า
8. **ขออนุมัติการนำเข้าต่างหาก:** ระบุขอบเขตข้อมูล เวลา cutoff เป้าหมาย แผนถอยกลับ และผู้ตรวจรับก่อนเขียนฐาน trial จริง; ห้าม live sync สองทางในรอบนี้

### 6.3 สัญญาที่ตัวนำเข้าต้องรักษา

- เก็บ source system, source record key, source timestamp, import batch และ mapping version; แยกเวลานำเข้าจากเวลาของเหตุการณ์
- มีตารางจับคู่ ID ต้นทางกับ ID ภายในและ unique constraints; นำเข้าซ้ำ/รันต่อหลังขัดข้องต้องไม่สร้างคนไข้ เงิน หรือตัดคลังซ้ำ
- คนไข้ที่บันทึกคู่ขนานก่อนวันนำเข้าต้องได้รับการจับคู่ ไม่สร้างเป็นคนใหม่เพราะมาจากคนละเส้นทาง
- รักษาความหมายของ missing/unknown, หน่วยยา เงิน วันที่/เขตเวลา และรหัสที่มีศูนย์นำหน้า; ข้อมูลไม่ผ่านต้องแยกออกให้คนตรวจ
- ข้อมูลเก่าแสดงว่าเป็นข้อมูลจากระบบเดิม ไม่ยกระดับเป็นการลงนามใหม่ใน CareFlow และไม่ย้อนแก้ snapshot ที่ลงนาม/ปิด Visit ไปแล้ว
- ประวัติการเงินและประวัติเคลื่อนไหวคลังที่นำเข้าเป็นหลักฐานอ้างอิง ไม่ใช่คำสั่งให้เกิดการรับเงินหรือเปลี่ยน stock ปัจจุบันซ้ำ
- เลือกช่วง snapshot/cutoff และวิธีตามรายการใหม่ระหว่างสองระบบอย่างชัดเจน ไม่มีการอ้างว่าข้อมูลครบถึง “ปัจจุบัน” จาก backup เก่า

## 7. แบ่งงานและลำดับส่งต่อ

งานมีหลาย subsystem จึงใช้เอกสารนี้เป็นแผนหลัก แล้วแตกแบบ/implementation plan ย่อยที่ตรวจรับได้ ไม่ส่งต่อเป็นคำสั่งก้อนเดียวว่า “ทำ production ให้เสร็จ”

| ชุดงาน | ขอบเขต/จุดเริ่มจากไฟล์จริง | ผลส่งมอบและการพึ่งพา |
|---|---|---|
| P0: รุ่นฐานและข้อกำหนด | Git/CI, README, `.github/workflows/ci.yml`, `package.json` | รวมงานที่อนุมัติ ตรึงรุ่น/หลักฐาน ทบทวนแบบนี้ และเก็บข้อมูลหน้างาน; ยังไม่ปลด synthetic guard |
| P1: Windows และ security boundary | `src/server/config.ts`, `src/server/app.ts`, `src/server/auth/`, `src/server/host-lock.ts`, `src/server/runtime.ts`, `src/server/lifecycle.ts` | แบบและแผน service/HTTPS/ACL/preflight/maintenance; ทดลองด้วยข้อมูลจำลองได้ก่อนมีฐานเก่า |
| P2: Recovery และ release | `src/server/db/client.ts`, `src/server/maintenance/`, scripts, CI | แบบและแผน backup/restore/upgrade/release bundle; กู้ข้ามเครื่องและพิสูจน์ service restart โดยยังใช้ข้อมูลจำลอง |
| P3: Real-data workflow | shared contracts, patient/platform/medication/inventory/finance/visit modules, client screens, migrations | แบบและแผน bootstrap ฐานจริง ลงทะเบียน/กลับมาใช้ ยา/ราคา สิทธิ์ เอกสารเทียบ; ห้ามใช้จริงจน P1/P2 และ safety checks ผ่าน |
| L1: สำรวจฐานเดิม | เริ่มหลังมีสำเนาที่อนุมัติเท่านั้น; ไม่มีไฟล์ฐานเดิมอยู่ใน repo | data dictionary, source mapping, ข้อจำกัดและแผน dry run; ทำคู่กับ P1/P2 ได้แต่ไม่ต้องรอเพื่อเริ่มสองชุดนั้น |
| L2: ตัวนำเข้าแบบควบคุม | อ้าง mapping ที่เจ้าของข้อมูลยืนยัน ไม่เริ่มจากการเดา engine | staging report, idempotency/reconciliation และข้อเสนอ import; ต้องอนุมัติก่อนเขียนฐาน trial |
| P4: ตรวจรับและ handoff หน้างาน | native Windows browser tests + อุปกรณ์จริง + คู่มือผู้ใช้ | เอกสารติดตั้ง/กู้คืนฉบับทดสอบแล้ว หลักฐาน UAT และลายเซ็น go/no-go; พึ่ง P1–P3 ส่วน L2 จำเป็นเฉพาะเมื่อเลือกใช้ข้อมูลนำเข้า |

หลังทบทวนแบบหลัก ให้เริ่มจาก P0 และแบบย่อยของ P1; การเลือก engine/ตัวเชื่อมต่อ legacy ต้องรอ L1 ไม่ขยายไปเป็น migration ทั้งฐานโดยปริยาย

## 8. เกณฑ์ตรวจรับก่อนเปิด Trial

ทุกข้อด้านล่างต้องมีผลตรวจของ **release เดียวกับที่จะติดตั้ง** ผลเก่าหรืออีกเครื่องไม่ใช้แทนหลักฐานหน้างาน

| Gate | หลักฐานที่ต้องมี | ผู้ยืนยัน |
|---|---|---|
| G0 ขอบเขต | รายชื่อบทบาท เครื่องหลัก จำนวนเครื่อง/ผู้ใช้พร้อมกัน วิธีใช้คู่ขนาน ขอบเขตบริการ รายการยาที่อนุมัติ และผู้รับผิดชอบ downtime | เจ้าของคลินิก + แพทย์ |
| G1 Release | รุ่น/commit/checksum ชุดติดตั้ง Windows, migration manifest, native-runtime probe, lint/typecheck/client/server/browser tests ผ่าน และทบทวน dependency/security findings ที่เกี่ยวข้องแล้ว | ผู้พัฒนา + ผู้รีวิว |
| G2 Patient/clinical | คนไข้ใหม่/กลับมาใช้/ชื่อซ้ำ/วันที่ไม่ทราบ/แพ้ยาไม่ทราบ/แก้ข้อมูล/สิทธิ์ผู้ช่วย และ snapshot หลังแก้ข้อมูล ผ่านทั้ง API และ browser | ผู้พัฒนา + แพทย์ |
| G3 ยาและเงิน | หน่วยยา ล็อตหมดอายุ จัด/ปล่อย/ส่งมอบ ยกเลิก/แก้คำสั่ง สองคนทำพร้อมกัน retry หลังคำตอบหาย ไม่มี stock/dispense/collection ซ้ำ และปิดวันตรงกับแหล่งเดิม | แพทย์ + ผู้ช่วย/การเงิน |
| G4 Windows/LAN | หลายเครื่องจริงเข้า HTTPS ได้โดยไม่มีคำเตือน แยก session, guest network เข้าไม่ได้ พอร์ตแอป/admin ไม่ถูกเปิด LAN; ทำ workflow เมื่ออินเทอร์เน็ตขาดได้ และทดสอบตามภาระพร้อมกันที่คลินิกระบุ | ผู้ดูแล + ผู้ใช้ |
| G5 กู้คืน | กู้บนอีกเครื่องจากสำเนาเข้ารหัสนอกเครื่องผ่าน ตรวจ cutoff/ความครบถ้วน/session และทำได้ตามเป้าหมาย; ทดสอบดิสก์เต็ม/สำรองล้มเหลว/เครื่องดับกับข้อมูลจำลอง | ผู้ดูแล + เจ้าของคลินิก |
| G6 อุปกรณ์/เอกสาร | ฉลากและ OPD ภาษาไทยอ่านครบ ไม่ตัดชื่อ/แพ้ยา/วิธีใช้ เครื่องสแกนถูกต้อง และใบเสร็จเดิมเชื่อมกับรายการ CareFlow ได้ | แพทย์ + ผู้ช่วย |
| G7 คนและการดูแลข้อมูล | บัญชีส่วนบุคคล การเก็บ recovery key นโยบายข้อมูล/สำรอง ช่องทางแจ้งปัญหาที่ไม่เผยข้อมูลจริง และผู้อนุมัติหยุด/กลับมาใช้ระบุครบ | เจ้าของคลินิก |
| G8 ซ้อมทั้งวัน | ซ้อมด้วยข้อมูลจำลองบนชุดติดตั้งจริงก่อนเปิดฐานจริง ตรวจทุก workflow ที่จะใช้ รวมงานค้าง/restart/คืนกลับระบบเดิม; ปิดข้อผิดพลาดที่กระทบคนไข้ ข้อมูล ยา เงิน หรือสิทธิ์ก่อนเริ่ม | ทีมคลินิก + ผู้พัฒนา |

หลังทุก gate ผ่าน เจ้าของคลินิกและแพทย์กำหนดช่วงเวลา/จำนวน Visit ที่รับเข้า trial และอนุมัติเริ่มด้วยลายลักษณ์อักษร ห้ามใส่ชื่อคนไข้จริงเพื่อ “ทดสอบว่าพร้อมหรือยัง” ก่อนผ่าน gate

## 9. Stop / กลับไปใช้ระบบเดิม / กลับมาเริ่มใหม่

หยุดรับรายการใหม่ใน CareFlow ทันทีเมื่อพบตัวตนหรือประวัติแพ้ยาผิด ยา/จำนวน/หน่วยผิด จ่ายหรือรับเงินซ้ำ ยอดผิด สิทธิ์รั่ว ข้อมูลที่ยืนยันแล้วหาย/เปลี่ยน หรือการสำรอง/กู้คืนไม่ผ่านเกณฑ์ การดูแลคนไข้ดำเนินต่อด้วยระบบเดิมตามผู้รับผิดชอบคลินิก

1. บันทึกเวลาที่เริ่มหยุด รุ่นระบบ และรหัสเหตุการณ์ในทะเบียนปัญหาที่ปลอดภัย หลีกเลี่ยงชื่อ/รายละเอียดคนไข้ในช่องทางผู้พัฒนา
2. รักษาฐานและไฟล์ประกอบไว้ ไม่ reset ไม่ลบ WAL/SHM ไม่แก้ข้อมูลตรง และไม่ลอง upgrade/restore ทับเพื่อให้หน้าจอกลับมา
3. ผู้ดูแลเก็บหลักฐาน/สำเนาอย่างสอดคล้องกันในพื้นที่ที่อนุมัติ แล้วตรวจสาเหตุบนสำเนา การเก็บหลักฐานนี้เป็นขั้นตอน incident ใหม่ ไม่ใช้คำสั่ง reset หรือข้อยกเว้นจากคู่มือ UAT เดิม
4. ไม่เปิด binary เก่าบน schema ใหม่ และไม่ restore backup ทับข้อมูลที่มีรายการใหม่โดยไม่มีแผน reconciliation; ถ้ายังพิสูจน์ทางย้อนกลับไม่ได้ให้ใช้ระบบเดิมต่อ
5. ผู้พัฒนาแก้และทดสอบด้วยข้อมูลจำลอง/ข้อมูลที่ลดความระบุตัวบุคคลแล้ว ผู้รับผิดชอบคลินิกตรวจรายการตกค้างและเหตุการณ์หลัง cutoff ให้ครบก่อนอนุมัติกลับมา

การถอยกลับเชิงปฏิบัติการคือกลับไปทำงานที่ระบบเดิม ไม่ใช่การลบประวัติ CareFlow หรือย้อนฐานโดยอัตโนมัติ

## 10. ชุดส่งมอบที่ต้องพร้อมเมื่อจะไปติดตั้งจริง

รายการต่อไปนี้เป็น **สิ่งที่ต้องผลิตและตรวจรับในงาน P1–P4 ยังไม่มีครบในรุ่นปัจจุบัน**:

- Windows release bundle ระบุ commit/runtime/native binaries/migrations และ checksum/provenance จากแหล่งแจกที่ตรวจสอบได้
- คู่มือติดตั้งทีละขั้น แยกเครื่องหลัก/เครื่องลูก สิ่งที่ต้องใช้ admin และสิ่งที่ผู้ใช้ทั่วไปทำได้ พร้อม preflight และเกณฑ์หยุด
- คู่มือเปิดคลินิก ปิดวัน ใช้คู่ขนาน เปลี่ยน/ปิดบัญชี และทบทวน backup
- คู่มือสำรอง กู้เครื่องใหม่ อัปเกรด incident และ reconciliation ที่ซ้อมจริงแล้ว
- checklist ผลตรวจ G0–G8, แบบบันทึกวัน trial และผู้อนุมัติเริ่ม/หยุด/กลับมาใช้
- เอกสาร legacy data dictionary/mapping/import report เฉพาะส่วนที่ทำแล้ว ไม่รวมฐานหรือข้อมูลคนไข้ใน repository

**จุดทบทวนถัดไป:** ให้ผู้ใช้ตรวจแบบหลักนี้ โดยเฉพาะระบบเดิมเป็นหลักอ้างอิง ขอบเขต trial และเป้าหมายกู้คืน จากนั้นจัดทำแบบย่อย/implementation plan ที่ลงมือทำได้ก่อนเริ่มพัฒนา ไม่มีการอนุมัติให้ deploy, import ฐานเดิม หรือเปิดใช้คนไข้จริงจากเอกสารฉบับนี้เพียงอย่างเดียว
