# เริ่มที่นี่ — ส่งต่องาน CareFlow ไป Windows ที่คลินิก

อัปเดต: 20 กันยายน 2026

**สถานะตอนส่งต่อ: ยังไม่พร้อมรับข้อมูลคนไข้จริง** เอกสารนี้ใช้รับงานต่อเพื่อทำให้พร้อม ไม่ใช่คู่มือให้เปิด production ตอนนี้

## 1. สิ่งที่ผู้ใช้เลือกแล้ว

- Repository หลัก: [ajbk/careflow-clinic](https://github.com/ajbk/careflow-clinic)
- ใช้ Windows หลายเครื่อง แยกผู้ช่วยกับแพทย์ในคลินิก
- เป้าหมายเป็น trial กับคนไข้จริง แต่ใช้คู่กับระบบเดิมก่อน
- จะมีฐานข้อมูลเดิมมาให้วิเคราะห์ภายหลัง ยังไม่มีไฟล์ ชนิดฐาน หรือสิทธิ์นำเข้าที่อนุมัติแล้ว

อ่าน [แบบแผนหลัก Production Trial](../superpowers/specs/2026-09-20-careflow-clinic-production-trial-design.md) ก่อนทำงาน แบบยังรอทบทวนฉบับเขียน; อย่าตีความการเลือกใช้คู่ขนานว่าอนุมัติลงมือทุก subsystem หรืออนุมัติ go-live แล้ว

## 2. ต้องเปิดโครงการไหนและใช้รุ่นใด

- พัฒนาต่อใน `careflow-pilot/`; `careflow-webapp/` เป็น prototype ที่หยุดพัฒนาแล้ว ไม่ใช่ระบบคลินิก
- ฐานงานแก้ความเสถียร: `6c1ae8a8336a00ec8b63fb8b9bb831aa15b24fb3` บน `codex/uat-stability-fixes`
- `main` ที่ตรวจตอนเขียนอยู่ที่ `952870c39e7a284971aa14464852a81eb7a381fe` ยังไม่มีงานแก้ความเสถียรนั้น ต้องตรวจสถานะ remote ใหม่ก่อนรับงาน
- [CI ของรุ่นฐาน](https://github.com/ajbk/careflow-clinic/actions/runs/35493606053) ผ่าน แต่ยังไม่ใช่หลักฐาน Windows หลายเครื่อง/อุปกรณ์จริง/backup-restore
- [Draft PR #2](https://github.com/ajbk/careflow-clinic/pull/2) เป็นคู่มือ synthetic UAT ไม่ใช่ production installer ห้ามนำคำสั่งในคู่มือเดิมมาใช้กับฐานจริงโดยเปลี่ยน path อย่างเดียว
- ก่อนเผยแพร่ ต้องรวมงานที่อนุมัติและสร้าง release ระบุรุ่น ไม่ติดตั้งบนเครื่องคลินิกโดยดึง working branch ล่าสุดโดยไม่ตรวจ

ไฟล์นี้อาจยังเป็น local commit บน Mac จนกว่าจะมีการ push ที่ยืนยันแล้ว หากหาไฟล์นี้บน GitHub/Windows ไม่พบ ให้ตรวจว่ารุ่นเอกสารถูกส่งขึ้น repository แล้วจริง ห้ามสรุปว่า push แล้วเพียงเพราะเอกสารระบุชื่อ repository

## 3. งานถัดไปสำหรับผู้พัฒนาที่รับต่อ

1. ตรวจ repository, branch, commit, working tree และเอกสารอนุมัติล่าสุด เก็บงานค้างของผู้ใช้ไว้ ไม่ reset/clean checkout
2. ขอทบทวนแบบหลักถ้ายังไม่ได้อนุมัติ แล้วแยกงาน P0–P4 กับ L1–L2 ตาม [ตารางแบ่งงาน](../superpowers/specs/2026-09-20-careflow-clinic-production-trial-design.md#7-แบ่งงานและลำดับส่งต่อ)
3. เริ่มรุ่นฐานและแบบย่อย Windows/security กับ recovery/release ด้วยข้อมูลจำลองได้ ไม่ต้องรอฐานเก่า แต่ยังไม่สร้างบัญชีหรือฐานสำหรับคนไข้จริง
4. จัดทำ implementation plan รายส่วนที่มีไฟล์เป้าหมาย วิธีทดสอบ เงื่อนไขผ่าน/หยุด และวิธีรับงานต่อ ให้ผู้ใช้ทบทวนและเลือกวิธีดำเนินงานก่อน implementation
5. หลังพัฒนา ให้ทดสอบชุดติดตั้งบน Windows จริง รวมหลาย browser/หลายเครื่องและ printer/scanner ไม่ใช้ผล Mac แทนผลหน้างาน
6. ประเมิน G0–G8 จากแบบหลักก่อนเสนอเปิด trial; หากมีข้อที่ไม่ผ่านให้รายงานว่าไม่พร้อม พร้อมระบุงานที่ยังขาด ห้ามลบคำเตือนเพื่อแสดงว่าพร้อมแล้ว

## 4. ข้อมูลหน้างานที่ต้องเก็บ — ไม่ต้องส่งข้อมูลคนไข้

ให้ผู้ดูแลบันทึกข้อมูลต่อไปนี้ในทะเบียนติดตั้งของคลินิกก่อนล็อกแผนติดตั้ง:

| เรื่อง | ต้องทราบเพื่ออะไร |
|---|---|
| เครื่อง Windows หลัก รุ่น/edition/architecture/RAM/พื้นที่ดิสก์ | ตรวจ runtime, native binaries, การเข้ารหัส และทดสอบภาระจริง |
| เครื่องลูกและจำนวนผู้ใช้พร้อมกัน | กำหนด browser และการทดสอบพร้อมกัน |
| LAN/Wi-Fi/DNS/IP และเครือข่ายผู้มาใช้บริการ | วาง HTTPS/firewall และแยก guest access; ยังไม่เปิดพอร์ตตอนเก็บข้อมูล |
| เครื่องพิมพ์ฉลาก/A4 และเครื่องสแกน | ทดสอบภาษาไทย ขนาดกระดาษ บาร์โค้ด และสิทธิ์เข้าถึงงานพิมพ์ |
| เครื่องหลักเปิดช่วงไหน ไฟฟ้า/UPS และ Windows Update | ออกแบบการเริ่มอัตโนมัติและการทำงานเมื่อระบบหยุด |
| อุปกรณ์สำรองนอกเครื่องและเครื่องที่จะใช้ซ้อมกู้ | พิสูจน์เป้าหมายสำรองไม่เกิน 15 นาที/กู้ภายใน 60 นาทีที่เสนอ ไม่ใช่เก็บไฟล์ไว้แล้วถือว่าผ่าน |
| ผู้รับผิดชอบคลินิก แพทย์ ผู้ช่วย/การเงิน และผู้ดูแลระบบ | ระบุใครตรวจรับ ใครหยุดงาน และใครอนุมัติกลับมาใช้ |
| รูปแบบ HN เดิม หน่วยยา หน่วยเงิน และเอกสารที่ใช้จริง | ป้องกันตีความข้อมูล/ราคา/หน่วยผิด; ใช้รูปแบบหรือตัวอย่างจำลอง ไม่ส่งรายชื่อจริง |

ยังไม่ต้องซื้อเครื่องหรือเปลี่ยนเครือข่ายตามการคาดเดา ให้ทดสอบกับทรัพยากรจริงและสรุปส่วนที่ขาดก่อน

## 5. เมื่อจะนำฐานข้อมูลเดิมมา

เริ่มจากชื่อโปรแกรมเดิม ชนิดฐาน/นามสกุลไฟล์ถ้าทราบ และโครงสร้างตารางที่ไม่มีข้อมูลคนไข้ ไม่ต้องอัปโหลดฐานทั้งก้อนเข้าแชตเพื่อเริ่มคุย

- ใช้ backup ที่สร้างถูกวิธีสำหรับฐานชนิดนั้น ไม่คัดลอกไฟล์ฐาน live แบบสุ่ม โดยเฉพาะเมื่อมี journal/WAL หรือหลายไฟล์ประกอบ
- ให้ผู้ใช้ระบุสำเนาและพื้นที่วิเคราะห์ที่อนุมัติอย่างชัดเจน ต้นฉบับเก็บแยกแบบไม่แก้ไขพร้อม checksum; หากต้องตรวจข้อมูลจริง ให้ประมวลผลในพื้นที่คลินิกและไม่แสดงรายแถวใน tool output/แชต
- เก็บไฟล์ฐาน/dump/config/credentials/PHI นอก checkout และนอก cloud sync; `.gitignore` อย่างเดียวไม่ใช่การป้องกันข้อมูลรั่วที่เพียงพอ
- ผลส่งมอบช่วงแรกคือโครงสร้างและคำอธิบายความหมายพร้อมความไม่แน่ใจ ไม่ใช่ตัว import หรือคำสั่งแก้ข้อมูล
- ทดสอบ mapping กับ staging และตรวจ HN ซ้ำ, ค่าว่างแพ้ยา, หน่วยยา, บาท/สตางค์, พ.ศ./ค.ศ., ยอดคลัง/เงิน และ cutoff ก่อนเสนอการนำเข้า
- แยกประวัติย้อนหลังจากธุรกรรมใหม่ ห้ามนำเข้าประวัติแล้วสั่งจ่ายยา ตัด stock หรือรับเงินจริงซ้ำ
- อย่าใช้บัญชีฐาน live หรือรหัสผ่านที่ส่งผ่านแชต และอย่ารัน dump/procedure/extension ที่ได้รับโดยยังไม่ตรวจ

รายละเอียดและเงื่อนไขอนุมัติอยู่ใน [งานฐานข้อมูลเดิม](../superpowers/specs/2026-09-20-careflow-clinic-production-trial-design.md#6-งานฐานข้อมูลเดิม--แยกจากการเปิดใช้งาน)

## 6. ข้อห้ามที่ต้องส่งต่อให้ครบ

- ไม่เปลี่ยน `synthetic_only`, ไม่แก้ migration เก่า และไม่ใช้ฐาน UAT เป็นฐานจริง
- ไม่เปิด `3001` หรือ admin endpoint ให้ LAN/WAN และไม่กดข้ามคำเตือน HTTPS
- ไม่ใช้บัญชี/รหัส UAT เป็นบัญชีคลินิก ไม่บันทึกรหัสใน repo หรือคู่มือ
- ไม่วางฐาน SQLite ที่เปิดใช้งานบน shared drive/OneDrive และไม่เปิด server หลายชุดเขียนฐานเดียวกัน
- ไม่ถือว่าคัดลอก `.sqlite` ได้คือ backup ผ่าน ต้องกู้และตรวจข้อมูลได้จริง
- ไม่ restore ทับฐานที่มีธุรกรรมใหม่ ไม่เปิด binary เก่าบน schema ใหม่ และไม่ลบ WAL/SHM เพื่อแก้ปัญหาล็อก
- ไม่ใส่คนไข้จริงเพื่อทดลองก่อนผ่าน gate และไม่ประกาศพร้อม production จากการเห็นหน้า login หรือ CI ผ่าน

## 7. สถานะไฟล์บน Mac ที่ต้องรักษา

ณ ตอนเริ่มเขียนเอกสาร มี README แก้ค้าง 8 บรรทัดเพื่อระบุ repository หลัก, `.DS_Store` และ `stitch_careflow_clinic_management_system/` เป็นไฟล์นอกชุดงานนี้ ต้องรักษาไว้ ไม่รวมโดยอัตโนมัติ ไม่ลบทิ้ง และไม่ย้ายไปปน release

ฐาน Mac ที่มีอยู่คือฐานทดลองเท่านั้น ไม่ต้องย้ายไปคลินิก และห้ามใช้ reset/การแก้ password/การ migrate กับฐานเดิมเป็นส่วนหนึ่งของงานเอกสาร การสร้างชุดคลินิกจะต้องแยกข้อมูลและผ่านแบบ/แผนที่อนุมัติ

## 8. เกณฑ์จบ handoff

ตอนนี้จบได้เฉพาะ **การส่งต่อบริบทและแบบเพื่อทบทวน** ยังไม่จบการเตรียม production

เมื่อจะส่งชุดพร้อมติดตั้ง ต้องมี release Windows ที่ตรวจแล้ว คู่มือติดตั้ง/เปิดปิดวัน/กู้คืนฉบับปฏิบัติจริง ผลตรวจ G0–G8 ผู้รับผิดชอบ และการอนุมัติเริ่ม trial ข้อมูลผู้ป่วยและรหัสลับต้องไม่อยู่ในชุดที่ส่งผ่าน GitHub

หลัง trial จบ การใช้ CareFlow เป็นระบบหลักและการเลิกระบบเดิมต้องเป็นการตัดสินใจใหม่พร้อมหลักฐาน ไม่เกิดขึ้นอัตโนมัติเพียงเพราะผ่านช่วงทดลอง
